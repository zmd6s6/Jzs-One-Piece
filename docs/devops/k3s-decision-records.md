# K3s 体系选型决策记录（ADR）

> 名词不熟先查：[术语表](./k8s-glossary.md)。机制层背景见[组件原理篇](./k3s-internals.md)，对应的事故复盘见[事故与原理](./k3s-incident-principles.md)。
> 每条记录：**背景 → 候选（含各自适用条件与代价）→ 本项目怎么选、为什么 → 什么条件下该换**。
> 说明：本文记录的是"当时条件下的选择"，不做普适推荐；同一条在别的约束下答案可能相反。

## 1. 容器平台：k3s / 标准 K8s / 轻量替代

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| k3s | 机器少（1~3 台）、离线交付、无人专岗运维 | 单二进制、安装快、组件内置（网络/DNS/存储）、airgap 离线安装成熟 | 默认数据存储是 SQLite（单副本，控制面无高可用）；默认组件固定，不熟悉容易踩默认值 |
| kubeadm 标准 K8s | 需要多控制面高可用、有专职运维、要跟云厂商/社区生态完全对齐 | 生态标准、etcd 可多节点、扩展面广 | 部署与升级成本高；离线安装组件多、依赖镜像多 |
| microk8s / minikube | 本机学习、开发自测 | 上手最快 | 面向开发体验，生产语义弱（网络、存储默认值不适合长期运行） |

**本项目选择**：k3s。约束是"客户现场机器少、无外网、交付要快"。
**什么条件下该换**：节点数 ≥3 且要求控制面高可用时，优先考虑带 etcd 的 k3s 模式或标准 K8s；团队有平台组时可直接上标准 K8s。

## 2. 节点拓扑：单节点 / 双节点 / 多节点

| 拓扑 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 单节点 | POC、演示、单机测试、明确接受停机的内部环境 | 最简单：无跨节点网络问题、无镜像分发问题 | 滚动更新必断服；节点故障即全停 |
| 双节点 | 只有两台机器、又希望"更新时不断服"的小环境 | 双副本可逐个滚动，单节点故障时服务可存活 | 引入两个新问题域：**镜像必须分发到两台**、**跨节点 Pod 网络（flannel 封装）必须通** |
| 控制面 1 + 工作节点 N（≥2） | 常见的小型生产形态 | 业务节点可扩缩，控制面负担稳定 | 控制面仍是单点；需要规划网络与存储 |
| ≥3 控制面（HA） | 要求控制面高可用 | 单机故障不影响调度与管理 | 运维复杂度、资源开销明显上升 |

**本项目的实际情况**：客户现场只提供了**两台服务器**，双节点是在这个资源约束下"能给滚动更新留余地"的折中，不是通用推荐做法。代价很快就出现了：镜像只导入了其中一台，另一台上副本长时间 ImagePullBackOff。
**什么条件下该换**：资源允许时按"1 控制面 + 多工作节点"规划；对可用性有硬要求时做控制面 HA。单节点也可以是好选择——只要环境允许停机，简单就是优势。

## 3. 镜像分发：私有 registry / 逐节点导入

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 私有 registry（如 registry:2） | 节点 ≥2，发版频率周级以上 | 推一次，各节点按需拉取；新增节点自动可用 | 多一个常驻服务；每个节点都要配 `registries.yaml` 并重启 k3s；明文 HTTP 需显式声明；仓库本身也要备份 |
| 逐节点 `ctr images import` | 单节点、离线且不允许新增常驻组件、发版频率低 | 零额外组件，完全离线 | 每次发版都要人工分发到**每个**节点，漏一个就挂；节点镜像被 GC 后可能重调度失败 |
| 更大规模的仓库（Harbor 等） | 多团队共用、需要漏洞扫描/权限体系/复制策略 | 功能完备 | 部署与运维成本高，对小环境属于过度配置 |

**本项目选择**：逐节点导入（现场断网、只有两台机器、发版不频繁）。为此专门加了"每个节点都要确认镜像存在"的检查步骤。
**什么条件下该换**：节点增加、发版变频繁、或需要给多套环境复用同一批镜像时，上 registry:2。

## 4. Java 产物形态与容器入口

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| fat jar + `java -jar` | 单体简单交付、不在意镜像体积与层缓存 | 一个文件，启动方式最直观 | 业务一改就重建整个大 jar，镜像层无法复用；与"薄 jar + lib 目录"的裸机交付形态不同，两条线要维护两套 |
| thin jar（ZIP 布局）+ `java -jar -Dloader.path=./lib` | 与裸机启动脚本统一口径、且能保证参数不被漏掉 | 裸机与容器同一套启动命令 | 启动依赖一个易被忽略的参数；该参数缺失时表现为"类根本加载不到"，排错不直观 |
| thin jar + `java -cp '/app/*:/app/lib/*' 主类` | 希望启动方式与打包布局解耦（NONE/ZIP 都能跑） | 显式类路径，不依赖 jar 的清单写法；`*` 展开目录下所有 jar，不介意文件名是否带版本号 | 需要约定运行包的目录结构（jar 在顶层、依赖在 lib/）；`/app/*` 会展开顶层所有 jar，不要在顶层堆无关文件 |

**本项目选择**：第三种。原因是发版与裸机两条线的产物形态相同（薄 jar + lib），而启动参数曾因"容器入口里漏写"导致过启动失败（见事故篇）。
**什么条件下该换**：如果团队统一走 fat jar 且不涉及裸机交付，`java -jar` 更省心；若强制统一 ZIP 布局并把它写进构建模板，第二种也可行——关键是**入口与布局必须成对固定下来**。

## 5. Dockerfile 放在哪：源码仓 / CI 内联 / 部署仓

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 源码仓 | 默认应当如此 | 与代码同版本演进；改动可评审；本地与 CI 构建一致 | 需要改 CI 引用路径 |
| CI 配置内联 | 临时验证、产物形态极其简单 | 改起来快 | 与代码分叉演进；入口藏在 CI 里不易评审；曾因内联入口漏参数发出过坏镜像 |
| 部署仓 | 镜像构建与部署清单强耦合、且由运维团队主导构建 | 构建与部署一处管理 | 构建关注点跑到运维仓；跨仓版本对齐麻烦 |

**本项目选择**：源码仓（三个服务仓各自持有自己的 Dockerfile），CI 只负责调用。
**什么条件下该换**：如果未来引入统一的构建平台（Buildpacks、镜像工厂），可以把构建逻辑上收，但仍应保留"构建定义随代码走"的原则。

## 6. 配置分层：kustomize / Helm / 多套 YAML+s脚本替换

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| kustomize | 环境数不多（2~5 个）、差异集中在少数字段（镜像、副本、配置、地址） | 无模板语言，渲染结果可直接 diff 评审；kubectl 内置 `-k`；不需要额外工具链 | 表达力有限：复杂条件渲染要写很多 patch；overlay 不能引用目录之外的单个文件 |
| Helm | 需要发布给别人复用、values 组合多、依赖社区 chart | 模板能力强、生态大、支持依赖与 hooks | 引入模板与 values 两层心智；渲染结果不易肉眼核对；chart 版本与 values 漂移是新的维护面 |
| 多套完整 YAML / 脚本替换 | 只有一套环境、几乎不变更 | 直观 | 环境一多就发散；sed 改字段是漂移与事故的常见来源 |

**本项目选择**：kustomize（base 放共性，每个环境一个 overlay）。
**什么条件下该换**：要对外发布部署包、或环境数与变量组合爆炸时，Helm 更合适。

## 7. 集群外中间件怎么被"叫到"（名字源方案）

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 配置里直接写 IP | 临时环境、永不更换后端 | 零机制 | 换地址要改多处配置；环境差异混进应用配置 |
| ExternalName | 目标是一个**域名**时 | 声明式、写法简单 | 目标写 IP 字面量时解析失败（DNS 层面无法把 CNAME 目标合成 IP 记录） |
| hostAliases（注入 Pod hosts） | 少量工作负载、临时兼容 | 生效快 | 要逐个工作负载声明；配置分散 |
| 节点 /etc/hosts | 节点上裸机进程 | 对节点进程直接生效 | Pod 不读节点 hosts；依赖它的同步机制不可靠 |
| 独立 DNS（dnsmasq / 公司 DNS 单一来源） | 中间件多、跨集群复用、希望"内外一套名字" | 一处维护、内外一致 | 多一个需要保活的服务，或需要网络管理方配合 |
| headless Service + 同名 Endpoints | 需要把集群外 IP 以**集群内名字**引用，且希望它进版本管理 | 声明式；只改 IP 即生效；Pod 与节点进程可各取所需 | 需要理解"同名绑定"机制；改完有约 30 秒 DNS 负缓存 |

**本项目选择**：headless + Endpoints（目标库是固定 IP，且希望配置进仓）。节点上的裸机进程另用 `/etc/hosts` 兜底。
**什么条件下该换**：中间件数量增多、或同一套配置要跨多个集群复用时，建独立 DNS 做单一来源更省心。

## 8. 探针怎么配

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 不配探针 | 试验性负载、明确人工值守 | 简单 | "Running"不代表可用；曾出现数据库已断连数天、界面仍显示正常的假健康 |
| 聚合健康端点 + initialDelay | 应用依赖很少、启动时间稳定 | 配置直观 | 任一外部依赖异常都会让端点变为失败，若配成 liveness 会反复重启健康进程 |
| 存活/就绪组端点 + startupProbe | 依赖较多、启动慢（数十秒到数分钟） | 探针只反映进程自身状态，不被外部依赖劫持；startup 覆盖慢启动 | 需要确认应用确实暴露了组端点（Spring Boot 在 K8s 环境默认启用） |
| tcpSocket 探测 | 无法提供 HTTP 健康端点时的兜底 | 总能配 | 只证明端口在监听，不证明应用可用 |

**本项目选择**：第三种（`/actuator/health/liveness|readiness` + startupProbe）。
**什么条件下该换**：非 JVM 或没有 HTTP 端点的服务用 tcpSocket；试验环境可以先不配探针，但不要把它当常态。

## 9. JVM 内存参数：显式数值 / 百分比

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 显式 `-Xmx` + `MaxMetaspaceSize` + `MaxDirectMemorySize` | 资源口径需要精确对账、环境间 limit 差异大 | 每项可解释；复盘时一目了然 | limit 调整时容易漏改其中一项，出现"堆够但 Metaspace 爆"这类问题 |
| `MaxRAMPercentage` / `InitialRAMPercentage` | 希望镜像默认值随 limit 自适应 | 部署侧只调 limit 即可；减少联动修改 | 只覆盖堆；Metaspace 与堆外仍需显式上限；limit 很小时需校验比例是否合理 |

**本项目选择**：过渡期用显式口径（并在文档里给出三类服务的目标值），计划把镜像默认值改为百分比方案。实践中的教训是：**不管选哪种，约束都是"堆 + Metaspace + 堆外 < limit"**。
**什么条件下该换**：镜像要被多个环境复用、limit 各不相同时，百分比方案维护成本更低。

## 10. 工作负载类型与存储

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| Deployment | 无状态、可随意替换的实例 | 滚动更新、回滚成熟 | 不适合需要稳定标识或本地数据积累的场景 |
| StatefulSet | 有本地数据（注册中心数据目录、影像临时文件） | 每个副本稳定名字与独立存储 | 数据在节点本地，副本漂移会落到别的节点 |
| local-path 存储 | 单/双节点、能接受"数据绑节点" | 零依赖，开箱可用 | Pod 重调度后数据不跟随；需人工确认数据在哪个节点 |
| 网络存储（NFS/Ceph/云盘） | 多节点、要求数据随 Pod 移动 | 副本可自由调度 | 多一套存储系统的运维成本 |

**本项目选择**：Deployment 承载无状态服务，StatefulSet 承载注册中心与影像服务；存储用本地目录型（local-path），并接受"数据绑节点"这一限制。
**什么条件下该换**：节点增多或要求故障自动恢复时，换网络存储，并补上 PodDisruptionBudget 与反亲和策略。

## 11. 版本与发布

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 从 git tag 构建，版本号多点绑定（tag = 镜像 tag = 制品版本） | 需要可追溯、可复现 | 同号同物，回滚与审计清晰 | 需要在流程上先打 tag 再构建 |
| 从分支构建（每次构建版本号手工给） | 内部快速迭代 | 灵活 | 同号不同物；曾出现 CI 连到同名旧副本仓、连续发出旧版本产物这类难察觉的问题 |
| 直接改集群镜像（`kubectl set image`） | 应急热修 | 立刻生效 | 不留痕、不回仓，下次 apply 即被覆盖 |

**本项目选择**：以版本号绑定为目标逐步推进；应急时允许临时改动，但必须在事后回写配置文件。
**什么条件下该换**：流程成熟后可以引入制品晋级（同一产物从测试晋级到生产），减少重复构建。

## 12. 观察方式：图形客户端 / 命令行

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 图形客户端（Lens/FreeLens 类） | 日常查看、应急时快速定位 | 状态树、日志、终端可视化，门槛低 | 界面里的改动不留痕，容易造成"改了集群没改配置仓" |
| kubectl / 配置文件 | 变更、脚本化、审计 | 可复现、可评审、可自动化 | 纯查看时不如图形界面直观 |

**本项目选择**：两者分工——图形界面看，命令行与配置仓改。这不是二选一，而是"观察与变更分离"。
**什么条件下该换**：不需要强制分离，但如果团队里有人用图形界面改生产，就需要明确这条边界。
