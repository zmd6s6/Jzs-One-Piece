# 容器不报任何错，却被反复杀掉：三起 OOM

> 先看：[JVM 内存白话](../../../backend/jvm-memory-anatomy.md)——堆/元空间/堆外的"厨房三区"类比。Java 占的内存是三块之和，容器限额管的是总和。

## 案例 A：堆超过限额（被杀 437 次）

**现象**：某服务反复重启，每次只活 14 秒，**日志一个字都没有**。

**推理**：日志干净说明不是程序报错——杀发生在 Java 层面之下。查 Pod 的 Last State（"上一次死因"）：`OOMKilled, 退出码 137`——操作系统干的。对照配置：容器限了 512MB，没配堆参数 → 程序默认要 1GB 堆 → 一启动就超。

**修复**：显式配置三块内存参数，确保"三块之和 + 零散开销 < 限额"。

## 案例 B：元空间被人为封顶

**现象**：报 `OutOfMemoryError: Metaspace`，但堆给了 6G 很富裕——**此时堆还空着一大半**。

**推理**：元空间（放"类的说明书"的柜子）被配了 `-XX:MaxMetaspaceSize=192m`，而这个服务要加载的类特别多（ORM 映射、报告生成库……）→ 柜子塞爆。这个数字是从别的服务的配置里抄来的。

**修复**：提到 512m（重业务服务的合理下限）。教训：**堆够 ≠ 内存够**。

## 案例 C：没配参数 = 信任镜像里的默认值

**现象**：服务平时正常，负载一上来就翻车。

**根因**：部署清单里没写内存参数，实际生效的是镜像里烘焙的旧默认值（1G/2G），与新环境限额长期不匹配——只是平时没触顶。

**预防**：内存参数与限额**成对**出现在部署清单里，并有"三块之和 < 限额"的固定检查项；根治方向是镜像默认值改百分比参数（`-XX:MaxRAMPercentage=70`，堆随限额伸缩），见[选型：运行时与配置](../decisions/runtime-and-config.md)。

## 判读口诀

- `Last State=OOMKilled`、无日志 → 查内存配置，别翻日志；
- 报 `Metaspace` → 查元空间上限，堆大小与此无关；
- 没显式配参数 → 去查镜像默认值配的是什么。
