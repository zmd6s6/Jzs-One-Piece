# 选型：平台与节点拓扑

> 返回[决策索引](./README.md)。每条含：候选（适用条件/优点/代价）→ 本项目怎么选、为什么 → 什么条件下该换。

## 1. 容器平台：K3s / 标准 K8s / 轻量替代

| 候选 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| K3s | 机器少（1~3 台）、离线交付、无人专岗运维 | 单文件、安装快、组件内置、离线安装成熟 | 默认数据存储 SQLite（控制面单点）；默认组件固定，不熟悉容易被默认值坑 |
| kubeadm 标准 K8s | 多控制面高可用、有专职运维、要与生态完全对齐 | 标准、etcd 可多节点、扩展面广 | 部署升级成本高；离线安装组件多 |
| microk8s / minikube | 本机学习自测 | 上手最快 | 面向开发体验，生产语义弱 |

**本项目**：K3s（客户现场机器少、无外网、交付要快）。**该换**：节点 ≥3 且要求控制面高可用时（K3s 带 etcd 模式或标准 K8s）。

## 2. 节点拓扑：单节点 / 双节点 / 多节点

| 拓扑 | 什么条件下合适 | 优点 | 代价与限制 |
|---|---|---|---|
| 单节点 | POC、演示、明确接受停机 | 最简单：无跨机网络、无镜像分发问题 | 滚动更新必断服；节点故障全停 |
| 双节点 | 只有两台机器、又希望更新不断服 | 双副本逐个滚；单节点故障服务可存活 | 引入两个新问题域：**镜像必须两台都有**、**跨机网络必须通** |
| 1 控制面 + N 工作节点 | 常见小型生产形态 | 业务节点可扩缩 | 控制面仍单点 |
| ≥3 控制面（高可用） | 要求控制面高可用 | 单机故障不影响调度管理 | 复杂度与资源开销上升 |

**本项目**：客户只有两台服务器，双节点是**资源约束下的折中，不是推荐做法**（代价很快兑现：镜像漏拷一台，副本挂了 5 小时，见[事故](../incidents/imagepullbackoff-missing-node.md)）。**该换**：资源允许时按 1+N 规划；允许停机时单节点也是好选择——简单就是优势。

## 3. 工作负载类型与存储

| 候选 | 什么条件下合适 | 代价 |
|---|---|---|
| Deployment | 无状态、实例可随意替换 | 不适合有本地数据的场景 |
| StatefulSet | 有本地数据（注册中心数据、影像临时文件）：每副本稳定名字+独立存储 | 数据在节点本地，副本漂移落到别的节点 |
| local-path 存储 | 单/双节点、接受"数据绑节点" | 零依赖开箱可用，但重调度不跟随 |
| 网络存储 | 多节点、要求数据随容器走 | 多一套存储系统的运维成本 |

**本项目**：无状态用 Deployment、有本地数据的用 StatefulSet + local-path（接受绑节点）。**该换**：节点增多或要求故障自动恢复时换网络存储，并补上反亲和策略。
