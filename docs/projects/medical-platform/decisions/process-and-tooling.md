# 选型：流程与工具

> 返回[决策索引](../incidents/README.md)。

## 1. 版本与发布策略

| 候选 | 什么条件下合适 | 优点 | 代价 |
|---|---|---|---|
| 从 git 标签构建（版本四处绑定） | 需要可追溯可复现 | 同号同物，回滚审计清晰 | 流程上要先打标签 |
| 从分支构建+手工版本号 | 内部快速迭代 | 灵活 | 同号不同物；曾连错同名旧仓库两个月（[事故](../incidents/ci-built-from-stale-repo.md)） |
| `kubectl set image` 直改集群 | 应急热修 | 立即生效 | 不留痕，下次 apply 被覆盖 |

**本项目**：以版本绑定为目标推进；应急改动必须事后回写清单。**该换**：成熟后引入制品晋级（同一产物从测试晋级生产）。

**回滚三式**（按代价排序）：`rollout undo`（最快，旧镜像须还在）→ 版本回退重 apply（可留痕）→ 整环境重建（灾难级）。

## 2. 观察方式：图形客户端 / 命令行

| 候选 | 什么条件下合适 | 代价 |
|---|---|---|
| 图形客户端（Lens/FreeLens 类） | 日常查看、应急定位 | 界面改动不留痕 |
| kubectl / 清单文件 | 变更、脚本化、审计 | 纯查看不如图形直观 |

**本项目**：分工而非二选一——**图形看、命令行和清单改**。边界要明确，否则有人用图形改生产就会造成"改了集群没改仓"。
