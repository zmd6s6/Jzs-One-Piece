# 同一条 SQL 手动正常、程序报"表不存在"——Oracle 权限缺失

> 机制基础：[Oracle 名字解析、同义词与权限](../../../backend/oracle-name-resolution.md)

## 一、事件链路

1. **T0**：客户现场程序日志持续报 `ORA-00942`，SQL 是一条三表关联（两表不带前缀、一表带 `H.` 前缀）。
2. **T1**：实施用 SQL 工具手动执行同一条 SQL——只读账号成功返回数据；另一业务属主账号报"表不存在"。
3. **T2**：因"手动正常、程序报错"怀疑程序侧：连接配置被覆盖？连了另一个库？对照研发环境同一接口正常、库端执行记录确认执行者就是配置写的账号。
4. **T3**：排查聚焦在表名解析（未加前缀按当前用户解析），在研发库复现验证成立——但解释不了程序失败（程序用的不是那个失败的账号）。
5. **T4**：DBA 检查现场库授权——**根因落定：程序账号对某张表缺 SELECT 权限**。补授权后立刻恢复。

## 二、思考链路

**假设 1：表不存在？** → 手测返回数据 → 排除。**（被骗：ORA-00942 的双重含义此时已埋下误导。）**

**假设 2：不同账号解析差异？** → 复现验证成立（解释了一个账号失败），但解释不了程序失败。**排查被这条线带偏两小时。**

**假设 3：程序连接被覆盖？** → 三环境对照排除。

**假设 4（DBA）：回到报错本身。** → ORA-00942 还意味着"无权限"——程序账号没有 SELECT 权限 → 一切闭环。

## 三、层层剖析

**表象**：同一条 SQL，手动正常、程序报错。

**直接原因**：程序账号对查询涉及的一张表没有 SELECT 权限。

**机制原因**：
1. ORA-00942 的双重含义（"不存在"与"无权限"共用报错）；
2. SQL 混用前缀导致不同账号手测结果不同，把注意力引向"解析"而非"权限"。

**流程原因**：新环境交付缺少"账号权限基线核对"步骤。

## 四、修复

```sql
GRANT SELECT ON 表属主.表名 TO 程序账号;
```

## 五、预防

1. 交付前以**程序账号**逐表核对 `all_tables`（返回 0 = 看不到）；
2. 授权脚本进版本库，随部署执行；
3. SQL 约定：跨账号访问一律写 `前缀.表名`，不混用。
