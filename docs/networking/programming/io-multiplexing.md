# 阻塞、非阻塞和 IO 多路复用：epoll 解决了什么问题

## 先看一个现象
单线程服务器在 `recv()` 等一位迟迟不发消息的客户端，其他请求也可能被堵住。想同时处理大量连接，就需要控制“等待 IO”的方式。

## 从阻塞开始
- **阻塞 IO**：调用者在没有足够进展条件时等待，像在一个窗口一直排队。
- **非阻塞 IO**：当前无法执行时尽快返回（如 `EAGAIN/EWOULDBLOCK`），应用稍后再试；像先取号去做别的事。
- **IO 多路复用**：一个线程等待多个描述符上的“可读/可写”等事件，像一名调度员盯多个取号窗口。

`select`、`poll`、Linux `epoll` 是不同的就绪事件等待接口；不是三种“网络协议”。**Reactor** 是把就绪事件分发给对应处理器的一种架构模式。

## 边缘触发和水平触发
**水平触发 LT**：只要条件依然成立，通常持续提示；**边缘触发 ET**：状态发生变化时触发。使用 ET + 非阻塞 IO 时，通常需要循环读/写直到返回 `EAGAIN`，否则可能留下未处理数据且不再获得期望的通知。

## 两个常见误区
1. 非阻塞不等于业务代码自动异步，仍需合理组织事件循环和后台任务。
2. `epoll` 不能让单线程 CPU 密集任务变快；事件循环中做长时间计算仍会拖慢所有连接。
