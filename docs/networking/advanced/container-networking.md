# 容器里能联网，为什么宿主机的网络结论不一定适用

## 先用生活问题理解这一篇

你把一个应用放进容器，它仍在这台电脑上运行，但突然发现容器里的 `127.0.0.1` 不是宿主机上熟悉的那个服务。因为不同网络环境可能各有自己的网络视图。

## 这些专业词分别是干什么的

- **容器**：让应用使用被隔离的进程和资源环境运行的一种常用技术。
- **网络命名空间**：Linux 把网络接口、路由等视图隔离给不同环境的机制，像各自有独立的内部电话表。
- **虚拟网卡（veth）**：常成对出现，用来连接两个网络空间的虚拟接口，像两端相连的虚拟网线。
- **Pod**：Kubernetes 组织一个或多个容器的基本运行单元，常共享同一网络空间。
- **Service**：Kubernetes 提供相对稳定的服务访问入口，而不是直接固定某一个 Pod 地址。

**前置知识**：[家庭网卡与路由器](../lan/home-network-devices.md) → [IP、路由](../ip-subnet-and-routing.md) → [NAT](../nat-and-port-forward.md)。

**最小观察或推演**：先画两间办公室，各自有电话和内部地址；再解释为何一间办公室里的 `localhost` 只指向它自己，不能直接当成另一间办公室的地址。

## 再回到真实技术现象
服务器主机能访问 `10.0.0.8:8080`，但容器内部连接失败。容器不一定共享宿主机的网络接口、路由表和 DNS 配置。

## 三个概念
- **网络命名空间 network namespace**：Linux 提供的网络隔离视图；像一栋楼里每间办公室都有自己的通信线路表。
- **veth pair**：成对出现的虚拟网卡，像连接两个网络空间的网线两端。
- **CNI**：为容器配置网络所使用的一套接口规范与插件生态；不同实现会选择不同的路由、隧道、策略和数据平面机制。

在 Kubernetes 中，**Pod** 内容器通常共享同一网络命名空间；**Service** 提供相对稳定的服务访问抽象，其具体转发实现可基于 iptables、IPVS、eBPF 或其他实现，不应统一断言“总是 DNAT”。

## 思考路径
```text
进程 → Pod 网络空间 → veth/虚拟网络 → 节点/跨节点路径 → Service/后端 Pod
```
每层可能涉及独立 DNS、路由、安全策略和端口映射。

## 实用命令（受控环境）
```bash
ip netns list
ip route
kubectl get pods -o wide
kubectl get svc
```
`kubectl` 仅适用于已配置访问凭据的集群；不要在生产集群随意修改网络规则。
