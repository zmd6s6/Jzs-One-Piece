# 打开一个网页，电脑与远方究竟发生了什么

## 从你每天做的事开始

你打开电脑，输入 `https://example.com`，几秒后页面出现了。你可以先只问一个问题：**网页原本不在我眼前，为什么我一点击，它就显示出来了？**

先不考虑任何英文缩写。把它想成去图书馆借书：

1. 你提出需求：“我要看这本书。”
2. 工作人员找到存放这本书的位置。
3. 有人把书送到你手里。
4. 你打开书，看到内容。

上网也是类似的过程：**找对方 → 把需求送过去 → 对方把结果送回来 → 浏览器展示结果**。这四句话就是第一次阅读应该掌握的全部主线。

## 先认识双方，而不是先背协议

- **浏览器**：打开网页的应用程序，比如 Chrome、Edge、Safari。它不只是显示文字，还会替你向远方获取网页内容。
- **客户端（client）**：主动提出需求的一方。你电脑上的浏览器就是客户端。类比：到餐厅点餐的顾客。
- **服务器（server）**：收到需求并提供内容的一方，可能是远方计算机上运行的网站程序。类比：接单、备餐的厨房。它不一定是一台专用的大机器。
- **请求（request）**：客户端发给服务器的一句话：“请给我某个页面。”类比：点菜单。
- **响应（response）**：服务器给客户端的回答：“找到了，这是内容”，或“没找到”。类比：厨房送上菜，或者告诉你这道菜没有了。
- **网络**：让不同设备可以交换数据的一套连接设施及规则。类比：连接顾客、厨房与配送员的道路。

把它连成一张最简单的图：

```text
你 → 浏览器（客户端） ─── 我要网页（请求）───→ 网站程序（服务器）
你 ← 浏览器显示页面 ←── 页面内容（响应）──── 网站程序（服务器）
```

注意：**浏览器不是互联网，互联网也不是某个网站**。浏览器是使用网络的一种程序；网上还可以传文件、发消息、打网络电话。

## 接下来会遇到的四个实际难题

知道两端之后，马上会有新问题。先了解问题本身，技术名称暂时不用记牢。

1. **对方在哪里？** 你知道网站名字，却不一定知道计算机的网络地址。后续的[域名与地址](./four-kinds-of-address.md)和[DNS](../dns-name-to-address.md)解决“找谁”的问题。
2. **中间怎么走？** 两台设备不在一起，数据要经过家庭路由器、运营商等网络设备。后续的[局域网](../lan/README.md)和[IP 与路由](../internet/README.md)解决“往哪里送”的问题。
3. **内容怎么可靠到达？** 一份网页可能要分成许多小份传输。如果途中丢失，需要有办法应对。后续的[传输层](../transport/README.md)学习这件事。
4. **双方怎么理解彼此？内容怎么保护？** 发送“我要什么”和返回“是什么”要有共同规则；涉及账号密码时，还要防止被偷窥或冒充。后续的[应用层与安全连接](../application/README.md)学习这件事。

这就是以后会看到的 IP、TCP、HTTP、TLS 等名字各自出现的理由。**现在只需知道它们对应不同问题，不要求你解释这些缩写。**

## 亲手观察一次，不写代码也能完成

1. 用浏览器打开 `https://example.com`。
2. 按 `F12`（或在菜单里打开“开发者工具”），选择 **Network（网络）** 面板。这个面板是浏览器记录自己对外取内容的地方。
3. 刷新页面。你可能看到一行或多行记录：每一行通常表示一次获取内容的尝试。
4. 点开其中一行，找 **Status（状态）**：它是对方回答的结果编号，例如 `200` 常表示成功；找 **Name（名称）**：它提示获取的是什么资源。
5. 关掉开发者工具，再回想：“哪一步是我发出需求，哪一步是对方返回内容？”

不同浏览器按钮、缓存行为可能不同；有些内容会直接从缓存获取，不一定每次真的访问远方。看不到完全相同的界面也不影响理解主线。

## 自己回答，算不算学会

- 浏览器、客户端、服务器分别是什么？用顾客与厨房类比回答。
- “网页打不开”能不能直接断定网站程序坏了？为什么还可能是找不到地址或中间网络不通？
- 用自己的话描述“提出请求 → 收到响应”，**不借用 TCP、DNS、HTTP 等缩写**。

能清楚回答，就继续学[为什么传送内容需要分工](./layers-and-encapsulation.md)。
