# HTTP/1.1、HTTP/2、HTTP/3 为什么都存在

## 先用一个生活问题入门

你去餐厅点了三道菜，店家规定必须把第一道完成后才能交付后一道，就可能排队。不同 HTTP 版本很大一部分改变的是“一条通道怎样高效处理多份订单”。

## 读技术细节前先认识术语

- **HTTP/1.1**：经典网页通信版本；可在可复用连接中发送多次请求，但传统响应排序存在限制。
- **HTTP/2**：在同一 TCP 连接上将不同请求组织成多个独立的逻辑流，像一条运输通道同时处理多单。
- **HTTP/3**：把 HTTP 语义承载在 QUIC 上的版本，流之间的传输阻塞处理不同。
- **多路复用**：共享一条连接传多条逻辑通信流，像同一配送车分别装多位顾客的订单。
- **QUIC**：运行在 UDP 之上的安全传输机制，能提供多个流和可靠交付；不是“UDP 直接变可靠”。

**建议已经学过**：[HTTP 是怎样点单的](./http-core.md) → [TCP 和 UDP](../transport/tcp-vs-udp.md) → [HTTPS 的保护](./https-tls.md)。

**先做一个最小验证或推演**：运行 `curl -I --http1.1 https://example.com`，看是否协商成功；不是所有 curl 构建支持强制 HTTP/2/3，务必通过实际响应确认而非只看参数名称。

## 把问题对应到实际网络
明明都叫 HTTP，抓包里 HTTP/1.1 能看到文本请求行，HTTP/2 却是二进制帧；HTTP/3 则经常看到 UDP 443。这是不同版本的底层承载和帧机制不同。

## 按演进理解
- **HTTP/1.1**：支持持久连接；传统情况下一个连接中的响应交付存在队头阻塞问题，浏览器通常会用多条连接缓解。
- **HTTP/2**：单个 TCP 连接上复用多条 HTTP 流，以二进制帧传输并支持头部压缩；但底层 TCP 丢包仍可能阻塞该连接的多个流。
- **HTTP/3**：HTTP 语义运行在 **QUIC** 上。QUIC 是基于 UDP 的安全传输协议，提供多条流和独立的可靠性机制，从而缓解 TCP 连接层队头阻塞。

## 关键不是“新版一定快”
实际性能受网络丢包、RTT、服务器支持、代理/CDN、客户端配置影响。某环境阻断 UDP 443 时，HTTP/3 可能不可用并回退到其他版本。

## 动手观察
```bash
curl -I --http1.1 https://example.com
curl -I --http2 https://example.com
curl -V
```
第二个命令取决于 curl 是否编译了 HTTP/2；HTTP/3 同样依赖客户端构建支持，不能仅看参数是否存在。
