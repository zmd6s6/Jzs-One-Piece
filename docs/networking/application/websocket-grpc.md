# WebSocket 和 gRPC 分别适合哪类通信

## 先用一个生活问题入门

客服聊天要你一句我一句持续交流；而查询订单往往是提问一次、拿结果一次。这两种业务为什么不总用同一种通信方式？

## 读技术细节前先认识术语

- **WebSocket**：建立后可双向持续交换消息的通信协议，像双方都能主动说话的电话。
- **轮询**：客户端隔一会儿就主动问“有新消息吗”，像每分钟打电话查一次。
- **RPC（远程过程调用）**：把调用另一台服务器的功能包装得像调用本地函数，像给外地分店直接下达办理指令。
- **gRPC**：一套以服务接口契约组织 RPC 的技术，常用 Protocol Buffers 编码并在 HTTP/2 上通信。
- **心跳**：在长连接中定期探测双方是否还可通信，像电话里偶尔问“还在吗”。

**建议已经学过**：[HTTP 请求与响应](./http-core.md) → [TCP 传输](../transport/tcp-vs-udp.md)。

**先做一个最小验证或推演**：为“实时聊天”和“查一次订单”分别画出双方交互顺序；理解不是什么项目只要实时就必须用 WebSocket，也不能把 gRPC 等同于普通函数调用。

## 把问题对应到实际网络
页面需要实时接收业务推送，服务 A 又要频繁调用服务 B。都能用 HTTP 轮询实现，但通信语义和效率未必合适。

## 两种常见工具
- **WebSocket**：在建立后提供双向消息通信通道，像电话双方随时说话；适合浏览器实时互动、实时通知等。连接持续存在需要考虑心跳、断线重连、鉴权、背压。
- **gRPC**：基于接口定义（常用 Protocol Buffers）提供类似调用本地函数的远程调用抽象，常基于 HTTP/2；适合明确类型契约的服务间 RPC，也支持流式通信。

**RPC（Remote Procedure Call）** 是“向远方服务调用函数”的编程抽象，并不能消除网络超时、不确定执行结果等分布式问题。

## 选择提示
需要浏览器实时双向消息，先考虑 WebSocket；跨语言内部服务、高频类型化调用，可评估 gRPC；普通资源查询和开放接口，REST/HTTP 往往更简单。
