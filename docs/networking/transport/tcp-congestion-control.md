# TCP 的流量控制和拥塞控制为什么是两套机制

## 先用一个生活问题入门

仓库的门只有一扇，卡车不能无限往里送；高速路上也可能堵车，即使仓库仍有空间。两种“不能继续猛发”的原因不能混淆。

## 读技术细节前先认识术语

- **流量控制**：考虑接收方还能接多少，像仓库空余库位决定发货上限。
- **拥塞控制**：考虑网络途中有多堵，像根据路况决定发车密度。
- **接收窗口 rwnd**：接收方告诉发送方的接收容量。
- **拥塞窗口 cwnd**：发送方据网络情况调整的在途数据限制。
- **往返时间 RTT**：一次信息与回应来回花费的时间。

**建议已经学过**：[ACK、重传和接收窗口](./tcp-reliability.md) → [高速公路类比](../advanced/network-performance.md)。

**先做一个最小验证或推演**：对照两个情境：A 是接收程序读取太慢；B 是网络中间发生丢包。分别指出更应该先观察接收窗口还是拥塞迹象。

## 把问题对应到实际网络
接收端 CPU 很慢，或者中间链路有大量竞争流量，TCP 都可能减速。但前一种是“接收方吃不下”，后一种是“道路太堵”，问题不一样。

## 两个窗口
- **接收窗口 rwnd**：由接收端接收缓冲决定，防止接收方内存压力；类似仓库剩余库位。
- **拥塞窗口 cwnd**：发送方根据网络拥塞信号调整，防止向网络注入过多未确认数据；类似司机依据路况控制发车量。

粗略地，在传统窗口模型中可认为发送方的在途数据受 `min(rwnd, cwnd)` 限制；真实吞吐还受 RTT、应用发包、发送缓冲、算法、整形等影响。

## 认识 RTT 与 BDP
**RTT** 是一次往返耗时；**BDP（带宽时延积）** 约为带宽 × RTT，是管道里可以同时容纳的数据量。示例：100 Mbit/s、100ms RTT，BDP 约 1.25 MB。大带宽高时延路径如果窗口太小，也无法跑满链路。

## 算法直觉
慢启动不意味着“一直慢”，而是从较小在途量逐步探测；遇到丢包或显式拥塞信号后算法会调整。Reno、CUBIC、BBR 的拥塞估计方法不同，不要只记一个“每次丢包就减半”的规则。

## 自测
为什么高延迟的跨地域链路可能需要更大的在途数据量？为什么调大接收缓冲不一定解决网络拥塞？
