# 电脑互发消息，为什么有时需要确认、有时直接发送

## 先不讲 TCP：想象两种送信方式

你要给朋友传一本书。如果少了一页、顺序乱了，这本书就不好读：你希望运输服务**按顺序交付、丢了会重送**。

但如果你正在玩实时游戏，角色的位置每隔很短时间更新。半秒前的旧位置即使现在补送，也可能没有意义。你可能更在意**尽快把最新消息送出去**。

网络给应用提供不同的传输服务。一个偏向“有序可靠地传内容”，一个偏向“把独立消息发出去，自己决定是否补救”。

## 两个正式名字，每个都解决一个问题

- **TCP（传输控制协议）**：向程序提供**可靠、有序的字节流**。可以类比持续通话中按顺序听到一段话：某部分丢失时会尝试重传。**字节流**就是一长串连续字节，不自动保留你每次发送了几句话的边界。
- **UDP（用户数据报协议）**：提供独立的**数据报**传输。像每次寄出一张明信片：发送的一张和接收的一张有独立边界，但 UDP 自身不保证每张一定到达、顺序正确或只到达一次。

这里说的“可靠”，指 TCP 传输层对字节流的交付承诺，**不是**“数据库一定保存成功”“接口一定执行成功”。

## 一张简单的对比图

```text
程序要发： [今天] [下雨了]

TCP 看见的是连续的字节序列：
  今 天 下 雨 了
接收方一次读取可能拿到“今天”，也可能拿到整段。

UDP 看见的是两份独立的数据报：
  第 1 份：[今天]
  第 2 份：[下雨了]
但其中某一份可能没有成功送达。
```

你在后面的[消息分帧](../programming/tcp-message-framing.md)会学到：程序可以给 TCP 字节流加“消息长度”，以便恢复业务消息边界。

## 为什么 TCP 要先打招呼

在 TCP 里，双方通常先**建立连接**，就像双方确认“这通电话开始了”，然后在连接中传递字节。连接初始需要同步序列号等状态；具体交互称为[三次握手](./tcp-connection-lifecycle.md)。

UDP 不先执行 TCP 式的握手；如果应用需要确认、重发或加密，可以在 UDP 之上自行实现，例如后面遇到的 QUIC。

## 具体例子与观察

- 下载压缩包：丢失一个字节都可能影响文件正确性，通常需要可靠的传输机制。
- 实时语音：可以使用允许应用控制丢失与延迟策略的机制，但不等于“语音必然使用 UDP”。
- 普通网页：HTTP/1.1 和 HTTP/2 常运行在 TCP 上；HTTP/3 运行在 QUIC 上，而 QUIC 又以 UDP 数据报承载，因此**不能简单说所有网页都是 TCP**。

在电脑上运行 `netstat -an`（Windows/Linux/macOS 通常可用），观察输出中是否出现 `TCP` 与 `UDP` 连接或端点；`UDP` 行通常不会显示类似 TCP 的连接状态。
