# 接口超时后能直接重试吗：区分超时、重试和幂等

## 先看一个现象
客户端发起“创建订单”，两秒后显示超时。到底有没有创建成功？**不知道。** 请求可能没有到达，也可能服务端执行成功但响应在返程丢失。

## 三个概念
- **超时 timeout**：等待某个操作的期限，像规定“最多等两秒”；它不是“远端已停止处理”的证明。
- **重试 retry**：再次尝试未确认完成的操作；像再次提交单据，可能导致重复。
- **幂等 idempotency**：一次或重复多次执行在业务效果上等价，像按同一唯一单号多次确认，不重复扣款。

## 稳妥方案
1. 给一次业务操作使用稳定的**幂等键**（如订单创建请求的唯一键）；重试沿用同一个键。
2. 服务端基于该键实现去重与结果查询，并处理并发冲突、存储事务和键的有效期。
3. 设置分层超时：连接超时、读写超时、请求总体截止时间（deadline）。
4. 只有适合重试的错误和操作才重试；使用指数退避与随机抖动，避免大量客户端同步重试。
5. 对可能已经执行的操作，优先查询状态或设计补偿流程。

## 误区
- TCP ACK 意味着字节获确认，并不意味着数据库事务提交。
- HTTP GET 通常应当设计为安全读取，但不能仅靠方法名假定实现一定无副作用。
- 超时设置越大不一定越稳定；延迟扩大可能加剧资源占用。
