# JVM 内存白话：堆、元空间、堆外到底是什么

## 先看一个现象

Java 程序在容器里被系统杀了，日志里**一个异常都没有**，查出来是"内存超限被杀"。可明明配置文件里写的是 `-Xmx2g`（堆最大 2G），容器也给足了 2G——为什么还超？因为**Java 进程占的内存远不止"堆"这一块**。用一个厨房的类比把三块内存讲清楚。

## 三块内存 = 厨房的三个区域

Java 虚拟机（JVM，运行 Java 程序的"引擎"）向操作系统要的内存主要分三块：

| 内存区 | 厨房类比 | 放什么 | 由谁配置 |
|---|---|---|---|
| **堆（Heap）** | 操作台 | 程序运行时创建的对象（订单、用户数据……）——最忙碌的区域 | `-Xmx`（上限）`-Xms`（起步大小） |
| **元空间（Metaspace）** | 菜谱柜 | "类的说明书"：每加载一个类（可以理解为引入一种新食材的做法），就存一份它的元数据 | `-XX:MaxMetaspaceSize`，不设则无上限 |
| **堆外内存（Direct Memory）** | 向邻居借的临时桌面 | 一些高性能框架（如网络框架 Netty）为了快，绕开堆直接向系统申请的内存 | `-XX:MaxDirectMemorySize` |

外加一些零散开销（线程栈、JIT 编译缓存），但大头是上面三块。

## 关键结论：容器限制管的是"整个房子"

容器（Docker/K8s）的 **memory limit 管的是整个房子**——操作台 + 菜谱柜 + 借来的桌面 + 所有零散开销的**总和**。所以这道算术题必须成立：

```text
堆上限 + 元空间上限 + 堆外上限 + 零散开销  <  容器 limit
```

**反例算一遍**：limit = 512MB，没配 `-Xms/-Xmx` 时程序默认要 1GB 堆 → 1GB > 512MB，一启动就被杀，日志毫无异常——因为不是程序报错，是操作系统直接"掀桌"（术语叫 **OOMKilled**，退出码 137）。

**再一个反例**：堆给了 6G 很富裕，但元空间被配了 `-XX:MaxMetaspaceSize=192m`，而程序要加载的类特别多（比如用了大量 ORM 映射、报告生成库）→ 菜谱柜塞爆，程序报 `OutOfMemoryError: Metaspace`——**这时操作台（堆）可能还空着一大半**。"内存够"永远指三块都够。

## 一个更省心的做法

现代 JVM 能感知容器限制，支持按百分比设堆：`-XX:MaxRAMPercentage=70` 意思是"堆 = limit 的 70%"，limit 变了堆自动跟着变，不用每次两头改。但注意：**百分比只管堆**，元空间和堆外仍要显式给上限。
